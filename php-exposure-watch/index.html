The problem in one breath

Unsupported = unpatched

When a PHP branch reaches end-of-life, the PHP project stops shipping security fixes for it. New flaws found after that date simply stay open on those servers. The code still "works", so nobody notices — until someone else does.

Self-service

Check a site you own

Type a domain you control. This page can't scan it for you (and shouldn't) — instead it builds copy-paste commands you run yourself, plus links to passive fingerprinting services. Everything runs on your machine against your site.

Tip: the cleanest answer is from inside your own server — run php -v on the box, or drop a one-line <?php echo PHP_VERSION; script behind auth. Headers can be hidden or stale.

Remediation

If you're on a dead branch

Confirm the real version

Headers lie. Check php -v on the server, or your hosting panel. Many distros backport security patches onto an old version number — if you're on supported distro packages, you may be safer than the banner suggests.

Plan the jump to a supported branch

Target PHP 8.3+ (ideally the newest). Use the official migration guides and tools like Rector and PHPStan to find breaking changes before you flip the switch.

Patch the stack around PHP too

Update your framework (Laravel / CodeIgniter / WordPress + plugins) and web server. An outdated CMS plugin is as common an entry point as old PHP itself.

Reduce what you advertise

Set expose_php = Off in php.ini and strip the X-Powered-By header. This isn't a fix — it just stops handing attackers a free fingerprint while you migrate.

Get real aggregate data (for this dashboard)

To turn the sample charts above into facts, pull aggregate counts from passive sources — Shodan, Censys, BuiltWith trends — and publish the percentages, not a per-organisation index.
